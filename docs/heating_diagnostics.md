# 난방 명령 확인과 CC 장애 조사

난방 제어 직후의 HA 표시는 사용자가 요청한 값을 즉시 반영한다.
실제 기기 응답 확인 여부는 같은 방의 **난방 명령 확인 상태** 진단 센서에서 확인한다.
기기 응답을 기다리도록 UI 반응을 늦추지 않으면서, 확인되지 않은 명령을 구분하기 위한 설계다.

## HA에서 확인하기

MQTT에 등록된 해당 방의 기기 페이지에서 진단 센서를 확인한다.
대시보드에도 센서를 추가할 수 있다. 기존 온도 카드 안에 경고가 자동으로 붙지는 않는다.
진단 센서는 기본 활성화되며, 난방이 구성된 방에만 등록된다.

| UI 상태 | 내부 값 | 의미 |
|---------|---------|------|
| 이력 없음 | `idle` | 시작 후 추적한 명령 없음 |
| 확인 대기 | `pending` | 요청을 받아 송신·응답 확인 진행 중 |
| 확인 완료 | `confirmed` | 실제 송신 이후 받은 유효 상태가 요청값과 일치 |
| 명령 미확인 | `unconfirmed` | 재시도 소진 또는 패킷 생성·전송 실패로 확인하지 못함 |

센서 속성에는 다음 정보가 포함된다.

- `request_id`: 해당 방에서 프로세스 실행 중 증가하는 요청 번호
- `requested`, `requested_at`: 요청값과 요청 시각
- `attempts`, `last_sent_at`: 실제 송신 완료 횟수와 마지막 완료 시각
- `last_received`, `last_received_at`: 마지막 유효 난방 수신값과 수신 시각
- `reason`: 미확인 또는 대기 사유
- `confirmed_late`: 미확인으로 종료한 뒤 일치하는 수신값을 확인했는지 여부

| 사유 | 의미 |
|------|------|
| `bus_busy` | 사전 정숙 검사 또는 송신 경계에서 버스 혼잡으로 전송을 연기함 |
| `response_timeout` | 송신 후 제한 시간 내 요청값을 확인하지 못해 재시도 대기 중 |
| `retry_exhausted` | 최초 송신과 네 번의 재시도 후에도 요청값을 확인하지 못함 |
| `invalid` | 송신할 패킷을 생성하지 못함 |
| `failed` | 전송 계층이 예외로 실패함 |

버스가 계속 바쁘면 송신을 기다리며, 실제로 보내지 않은 요청은 재시도 횟수에 포함하지 않는다.
송신한 요청의 시간 초과는 버스 혼잡이나 주기 조회 여부와 무관하게 판정한다.
요청값과 다른 응답도 마지막 수신 정보에 남지만 확인 완료로 처리하지 않는다.

새 요청은 이전 요청을 대체한다. 이전 요청의 송신 결과가 새 요청의 횟수·결과를 바꾸지 않는다.
같은 프로세스에서 MQTT만 재연결되면 현재 결과를 재발행한다.
애드온을 재시작하면 `이력 없음`으로 초기화하며 이전 명령의 확인 결과를 복원하지 않는다.

## 확인 결과의 한계

`확인 완료`는 프로토콜 상태값의 일치를 뜻한다. 물리적 가열이나 난방수 순환을 보증하지 않는다.
`명령 미확인`도 실제 기기 동작 실패를 확정하지 않는다.
응답 누락·손상 또는 다른 조작으로 인한 상태 불일치일 수 있다.

현재는 응답과 특정 송신을 일대일로 연결하는 식별자를 사용하지 않는다.
따라서 제어 응답과 주기 조회 응답을 인과적으로 확정하지 않고, 송신 이후의 상태 일치를 확인한다.
실제 쓰기 이전에 받은 일치 상태나 HA 디버그 입력은 확인 근거로 사용하지 않는다.
첫 송신이 실패해 재연결을 기다리는 동안 받은 상태도 이후 송신의 확인 근거에서 제외한다.
실제 쓰기 뒤 `drain` 대기 중 도착한 빠른 응답은 송신 완료 결과와 함께 확인한다.
응답 없는 동안 HA에는 낙관적 요청값이 남을 수 있으므로 진단 상태와 함께 읽는다.
기존 난방 엔티티의 가용성을 명령 실패만으로 변경하지 않는다.

## 로그 활성화와 추출

일반 로그에는 요청·송신 완료·시간 초과·소진과 마지막 수신 정보를 남긴다.
송수신 원본, 버스 혼잡에 따른 송신 연기, 프레임 폐기 상세는 `debug` 수준에서 기록한다.
상세 기록을 켜기 전의 원본은 소급해서 복구할 수 없다.

1. 조사 전에 애드온의 `advanced.loglevel`을 `debug`로 설정한다.
   실행 중 변경하려면 MQTT 발행 도구에서 다음 메시지를 retain 없이 발행한다.

   ```text
   토픽: wallpad/bridge/config/log_level
   메시지: debug
   ```

2. 애드온 로그에서 `event=file_logging_ready`와 저장 경로를 확인한다.
   애드온의 기본 보존 경로는 `/share/wallpad-mqtt-bridge/log/kocom.log`다.
   공유 마운트가 없는 로컬 실행은 작업 디렉터리 아래 `log/kocom.log`를 사용한다.
3. 현재 파일과 회전 파일 `kocom.log.1`부터 `kocom.log.10`을 함께 추출한다.
   파일당 회전 기준은 1 MiB이며, 현재 파일과 백업을 합해 약 11 MiB를 보존한다.
   보존 시간은 트래픽에 따라 달라진다.
4. HA의 `/share`를 읽을 수 있는 파일 도구로 로그 폴더를 복사한다.
   같은 공유 경로를 볼 수 있는 셸에서는 다음과 같이 묶을 수 있다.

   ```bash
   tar -czf /share/wallpad-mqtt-bridge/heating-diagnostics.tar.gz \
     -C /share/wallpad-mqtt-bridge log
   ```

5. 조사 후 MQTT 로그 수준을 `info`로 되돌린다.
   시작 시 `event=file_logging_unavailable`이 보이면 파일 보존이 되지 않으므로
   콘솔 로그를 확보하고 공유 경로의 쓰기 권한을 확인한다.

공유 경로에 있는 원본에는 방 이름·조작 시각·상태 등 생활 정보가 포함될 수 있다.
공개 이슈에는 원본 대신 식별 정보와 생활 정보를 제거한 재현 자료를 첨부한다.
센서 속성 시각은 UTC 오프셋을 포함하고, 일반 로그 시각은 실행 환경의 시간대를 따른다.
서로 비교할 때 시간대를 함께 확인한다.

## 로그를 읽는 순서

먼저 방과 `request_id`로 요청을 찾고 송수신 시각·원본을 함께 비교한다.
요청 번호는 방별·프로세스별 값이므로 기동 로그 경계도 확인한다.

| 기록 | 확인할 내용 |
|------|-------------|
| `heating_requested` | 요청 모드·온도와 새 요청 번호 |
| `tx_frame source=control` | 실제 쓴 원본과 요청 번호 |
| `tx_frame source=poll` | 주기 조회의 송신 순서 |
| `tx_deferred` | 버스가 바빠 보내지 못했는지 |
| `rx_frame` | 수신한 유효 프레임 원본 |
| `rx_discard reason=checksum` | 체크섬 불일치와 기대·수신 체크섬 |
| `rx_discard reason=tail` | 종료 바이트 손상 |
| `rx_discard reason=resync` | SOF를 다시 찾으며 폐기한 바이트 묶음 |
| `rx_discard reason=incomplete` | 수신 태스크 종료 시 남은 불완전 데이터 |
| `parse_skip`, `frame_unhandled` | 길이 부족·미지원 타입 등 해석하지 못한 프레임 |
| `heating_deferred` | 사전 검사 또는 송신 경계의 혼잡 대기, 같은 사유는 한 번만 기록 |
| `heating_response_timeout` | 해당 요청의 응답 확인 시간 초과 |
| `heating_unconfirmed` | 종료 사유, 횟수, 마지막 유효 수신값·시각 |
| `heating_confirmed` | 상태 일치와 뒤늦은 확인 여부 |
| `heating_superseded`, `heating_superseded_write` | 새 명령에 의해 대체된 요청·송신 결과 |

정상 수신 원본은 있어도 해석 실패가 있을 수 있다.
또한 파싱된 `target_temp`는 off·외출 모드에서 이전 확인값이나 초기값을 유지할 수 있으므로,
그 모드에서는 온도 필드를 요청 확인 조건에 넣지 않는다.

## 격리 환경 조사 절차

다음 정보부터 기록한다. 현재 장애 당시 배포 커밋과 상세 구성은 추가 확인이 필요하다.

- 배포에 사용한 Git 커밋·이미지 식별자와 애드온 버전
- 소켓 또는 시리얼 구성, 변환기 모델·펌웨어·연결 수와 통신 설정
- `scan_interval`, `packet_delay`, 방별 난방 주소
- 장애·CC 표시·복구 시각, 다른 기기의 통신 상태
- 확보한 로그 범위와 격리 검증 환경 유무

공개 자료에서는 호스트·계정·방 이름 등 식별 정보를 제거한다.
실제 주거 환경에서 제어 불능이나 과열을 유도하지 않는다.

1. 단일 난방 명령과 정상 응답을 비교한다.
   온도 변경 요청 하나가 모드와 온도를 포함하는 한 프레임으로 나가는지 확인한다.
2. 새 명령을 이전 명령의 전송 대기 중에 넣어, 마지막 요청이 추적되는지 확인한다.
3. 난방 응답을 누락·지연하거나 요청값과 다르게 공급한다.
   실제 송신 다섯 번 이후 미확인 표시와 경고가 일치하는지 확인한다.
4. 체크섬·종료 바이트 손상과 잡음을 넣은 뒤 정상 프레임을 공급한다.
   손상 프레임으로 확인 완료가 되지 않고 정상 프레임에서 복구되는지 확인한다.
5. 난방 응답이 없는 동안 조명 등 다른 기기의 정상 수신을 공급한다.
   난방 문제와 버스·연결 전체의 문제를 구분한다.
6. 소켓 EOF를 공급해 기존 재연결 경로를 거친 뒤 정상 수신으로 복구되는지 확인한다.
7. 미확인 후 일치하는 응답을 공급해 뒤늦은 확인을 구분한다.

자동화와 수동 조작, 특정 명령·송신 타이밍·기기 내부 이상은 모두 조사 후보다.
관측한 순서만으로 장애 원인을 단정하지 않는다.

## 이번 변경으로 확인한 사실과 남은 검증

테스트에서 목표 온도 요청 한 번에 동일한 설정 프레임을 두 번 생성하는 경로를 확인했다.
모드·온도를 한 방의 요청으로 묶고, 최초 송신과 네 번의 재시도 예산을 적용했다.
소켓 EOF가 재연결을 우회하는 경로와 종료 바이트 손상을 놓치는 검증도 보강했다.
각 동작은 실패 테스트를 먼저 실행한 뒤 구현하고, 전체 검사가 통과한 상태로 커밋했다.

기존 온도 필드 반영 중 내부 모드를 heat로 설정하는 동작은 유지했다.
명령 확인은 그 내부 모드 대신 검증된 실제 수신값으로 판정한다.

현재 확인한 코드 문제와 CC 제어 불능의 인과관계는 입증되지 않았다.
실제 기기와 격리 하드웨어를 이용한 재현·복구 검증은 수행하지 않았다.
컨트롤러 전원 재투입 외의 복구 조건, 통신 장애 시 송신 중단·백오프 정책은 추가 검증 대상이다.
재연결 래퍼 내부의 연결 복구 대기는 기기 응답 시간 초과와 별개이며,
진단의 송신 횟수는 전송 계층이 완료로 반환한 송신만 센다.

통합 시나리오는 다음 명령으로 하드웨어 없이 실행할 수 있다.

```bash
source .venv/bin/activate
pytest -q tests/wallpad/apps/panel/test_heating_scenarios.py \
  tests/wallpad/apps/panel/test_heating_commands.py \
  tests/wallpad/apps/panel/test_heating_diagnostics.py \
  tests/wallpad/apps/panel/test_panel_receive_packets.py \
  tests/wallpad/transport/test_socket_transport.py
```
